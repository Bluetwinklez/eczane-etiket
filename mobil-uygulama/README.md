# Eczam Mobile — Capacitor iOS Shell

A thin native shell around the Eczam mobile web application served at `/mobil/`. It needs a running Eczam server; installing the shell does not install a pharmacy database or server.

## Development

Use Node 22 or newer. iOS compilation, signing and local Xcode use require macOS and an appropriate Apple development environment.

```bash
npm ci
npm test
npm run senkron
npm run ios:ac
```

`senkron` prepares `www/` and synchronizes the iOS project. `ios:ac` opens Xcode. The project uses Swift Package Manager. `www/` contains the connection screen; `scripts/hazirla.js` copies shared assets from `web/public/`.

## Connecting

Temporary TestFlight mode (`DOGRUDAN_DEMO` in `www/baglan.js`) opens the public demo directly, without discovery or address entry. The `?demo=1` launch automatically signs into the public sample account only when the server advertises demo mode. Internet is required; each demo browser session receives a separate sample database. Saved pharmacy addresses are preserved. Profile → change server (`?degistir=1`) still opens the connection tools. Set the flag to `false` to restore normal startup.

On first launch the shell looks for an Eczam server on common private network ranges at port 3000 using `/api/health`. It saves a discovered server address and loads its `/mobil/` page. You can enter an address manually, including when discovery cannot find the server. An unreachable saved local address triggers rediscovery.

Internet addresses require HTTPS. HTTP is allowed only for supported private/local addresses. Keep phones and the pharmacy server on a trusted network. The broad Capacitor navigation setting supports different pharmacies' server addresses; only connect to a server you trust.

The user agent includes `EczamApp/1.0`, enabling the mobile interface's server-switch control.

## Mobile reliability and private demo sessions

- Queueable count, request-book and temperature writes are saved before sending. Failed writes remain visible under Profile → pending records, with explicit retry/removal controls. Local storage failures are reported instead of silently claiming success.
- A single drain runs per app view. Stable `Idempotency-Key` values let the server return the original response after an interrupted connection without repeating the database mutation. Successful writes and deduplication records commit together; those records are included in backups.
- Pending records carry their account ID. Legacy/unowned or other-account records require review and are never silently sent as the current account. Logout warns before discarding pending records, clears cached account data and reloads to clear memory.
- Product results load in batches of 80 until all matches are reachable; searches reset the limit. Connection failures are distinguished from empty search results.
- Notes mode supports single or batch scanning. Batch mode removes duplicates and holds at most 500 codes in memory for the current screen. Sharing/copying requires a tap and never sends scan text to the Eczam server. Leaving the screen discards the batch.
- With `ECZAM_DEMO=1`, API requests use a private database cloned from the seeded sample. The session ID is generated by the server, preserved across login renewal, and stored in the HTTP-only session cookie. Audit writes use the same private database. Normal pharmacy deployments keep their existing database behavior.
- Demo data is temporary: it resets on server restart/deploy, session expiry/logout, or after eight hours without activity. Up to 100 temporary spaces are allowed per process; excess requests receive a retryable 503. Demo data is unsuitable for real pharmacy records.

Automated tests cover retry deduplication, validation failures, overlapping drains, storage failures, cross-account queues, demo isolation (including audit records), batch sharing, and product pagination. Real-device camera/Notes testing is still required.
